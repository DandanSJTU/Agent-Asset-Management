## 工作场景
适用于首页信息流（T 站 + C 站）策略类需求的提出、定义与立项：从「有个想法」到「团队决定做或不做」。核心是用 1-2 Page Spec + 可点击原型替代长 PRD 与需求评审会，把协调时间压到最低，让决策周期从 2-4 周缩到 1-2 天。

## 适用条件
- 想法来自任何人（Side Quest 产物、Badcase 归因、竞品观察），需要快速判断做不做。
- 需求涉及多角色（产品 / 工程 / 算法 / 测试），传统的层层汇报成本高于实现成本。
- 方案尚未验证，需要用最小代价拿到团队共识而不是预算审批。

## 核心 SOP
- 想法先做 Side Quest 原型：利用碎片时间产出可点击 demo，用原型说话，不写 PPT 争资源。
- Spec 固定四段：背景（问题 + 证据）/ 方案（含影响面与回滚）/ 指标（主指标 + 护栏指标）/ 验收（通过线 + Evals 集），控制在 2 页内。
- 团队看 demo → 集体决策 → 当天决定 Ship / Kill，未通过的不进需求池。
- 拍板后只登记到实验线与 Spec 台账，不另开需求评审会。

## 判断逻辑
- 原型 > 文档：一个能点的 demo 比 15 页 PRD 更快暴露产品判断分歧。
- 验收前置 > 事后评估：Spec 里先写通过线，避免实验跑完再争论"算不算成功"。
- 双平台双场景 > 汇总口径：T 站 / C 站、行前 / 行中的影响必须分开说明，汇总会掩盖一边涨一边跌。
- 证据分级 > 结论强弱：区分现象 / 相关 / 因果并标注证据强度，不把相关性说成因果。

## 禁忌与反模式
- 不要写长 PRD：15-30 页文档的信息密度低于 2 页 Spec + 原型。
- 不要用汇总口径掩盖分平台差异：行中涨、行前跌的混排结论会误导决策。
- 不要在没定通过线时开实验：事后定义成功标准等于没有标准。
- 不要把"团队正在讨论"写成确定结论：未拍板事项必须显式标注状态。

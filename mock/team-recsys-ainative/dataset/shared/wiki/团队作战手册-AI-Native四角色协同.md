# 团队作战手册 · AI-Native 四角色协同

> 团队形态：4 人 AI-Native 小队（2 Builder / Full-stack Eng + 1 Product-Engineer Hybrid + 1 Design-Engineer Hybrid），
> 映射到本业务域的四个席位：**产品 / 工程 / 算法 / 测试（QA + Evals，约 0.5 人）**。
> 一句话：4 人 ≈ 传统 15 人产研 UED 团队，差异不在人更少，而在角色融合 + AI 承担 80% 执行工作。

## 一、四个席位与 AI 分工
| 席位 | 核心职责 | 与 AI 怎么协同 | 传统对应 |
|---|---|---|---|
| 产品（PE Hybrid） | 产品决策、1-2 Page Spec、原型、review AI 代码 | AI 辅助调研、生成原型；Spec 替代 PRD；人做产品判断与优先级 | PM 1-2 + 项目经理 1 |
| 工程（Builder） | 写代码、做架构、生成 UI、定义 evals | AI 一次生成全栈代码；日 review 3000+ 行（手写 50-200 行）；人做架构决策与把关 | 前端 2-3 + 后端 2-3 + 设计 1-2 |
| 算法（Builder） | 召回 / 排序模型迭代、实验设计与分析 | AI 跑离线分析与批量实验；人定假设、判 tradeoff、定推全 | 算法 2-3 |
| 测试（QA / Evals） | 质量标准与 Evals 维护、Badcase 归因、发布门禁 | Evals-driven + AI 自动化测试，约 0.5 人维护；人做最终确认 | QA 1-2 |

## 二、协同机制（去中心化自主）
```
任何人有 idea
  → Side Quest 原型（碎片时间自主发起）
  → 团队看 demo（原型即说服力，不用写 PPT 争资源）
  → 集体决策（Evals 验证质量）
  → Ship / Kill（当天决定）
```
四大特征：**无 handoff**（设计直接 ship 代码）、**无联调**（AI 一次生成全栈）、**全局透明**（4 人天然低协调成本）、**AI 作隐形项目经理**（进度跟踪人工干预约 3%）。

## 三、决策速度对照
| 环节 | 传统 | AI-Native |
|---|---|---|
| 有 idea → Ship/Kill | 2-4 周（层层汇报、PPT 评审） | **1-2 天**（原型 + Evals + 团队共识） |
| 协调时间占比 | ~45% | ~12% |
| 构建时间占比 | ~55% | **88%** |

## 四、本业务域的角色接口
| 事项 | 主责 | 协同 |
|---|---|---|
| 需求 Spec 与验收 | 产品 | 算法给指标、工程给影响面、测试给 Evals |
| 指标口径 | 产品 + 测试 | 算法/工程出数时必须带口径 |
| 模型 / 策略上线 | 算法 | 工程管发布与回滚、测试管门禁 |
| 配置变更 | 工程 | 算法给参数、测试给回归、产品给护栏 |
| 线上问题 | 工程初判 | 算法归因模型、测试补 Evals、产品判业务影响 |
| 内容治理 | 产品 | 算法出打压策略、测试给误伤率基线、工程配开关 |

## 五、风险与缓解
| 风险 | 说明 | 缓解 |
|---|---|---|
| 单点故障 | 4 人缺少 backup | 文档化 + AI 可接手部分工作（本 Wiki 即载体） |
| 质量风险 | AI 生成代码可能有 bug | Evals + Human review 双重保障 |
| 知识孤岛 | 一人掌握某环节黑话 | 通道字典 / 口径速查 / 台账全部落 Wiki |

## 六、团队硬约束（跨角色通用）
1. 任何结论必须带口径（pv/uv、体系、底表、实验号）。
2. 未拍板的事写「团队正在讨论 / 待确认」，不包装成确定结论。
3. 任何上线必须有开关与回滚路径，且已验证。
4. Evals 通过线前置定义，全量回归不抽样。
5. 区分现象 / 相关 / 因果，并标注证据强弱。

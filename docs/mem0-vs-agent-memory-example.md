# mem0 记忆增量演示：以推荐策略研发为例

> 本文基于一段测试对话整理，用「推荐策略研发工程师」的工作场景，说明 mem0 相对于 LLM Agent 自身记忆带来的增量价值，并澄清一个常见误解：**Claude Code 等 Agent 在会话之间是「失忆」的**。

## 一、场景设定

假设你是某 App 的**推荐策略研发工程师**，已经用 mem0 跟 LLM 聊过两轮，沉淀了以下项目记忆：

- 你负责推荐系统**召回策略**，主要用**双塔模型**和 **FM**
- 之前 CTR 掉了 0.3%，怀疑是**用户冷启动问题**
- 试过用 item title embedding 做 content 特征，**效果不明显**
- 怀疑**多目标优化里「时长目标」和「CTR 目标」冲突**
- AB 实验平台用 **hash(user_id)** 分桶，线上有偏移
- 怀疑**模型热加载导致线上 serving 不一致**

---

## 二、对话示例：embedding 维度调整引发的线上 CTR 下降

新的一轮问题：

> "上周把双塔的 user embedding 维度从 64 调到 128，离线 AUC 涨了 0.8%，但线上 CTR 反而降了 0.1%，奇怪。"

### 2.1 没有 mem0

LLM 只看到你最新这条消息，对上下文一无所知：

> "可能是过拟合了，建议检查一下线上和离线的特征分布是否一致。可以试试加正则化。"

回答很通用——因为它不知道你已经在冷启动问题上踩过坑、AB 实验平台有 serving 不一致的问题、之前试过哪些方案。

### 2.2 有 mem0

搜索到相关记忆后，prompt 里会注入上述 6 条事实。LLM 拿到上下文后，回答完全不同：

> "Alex，等一下——结合你之前的情况，这个现象更像是你提到过的**模型热加载导致的 serving 不一致**问题。你上次说 bucketing 用的是 hash user_id，线上有偏移。
>
> 我建议先排查两件事：
>
> 1. **新模型和旧模型是不是同时在 serving** —— 如果是热加载切换，部分流量可能还在用旧模型，导致 CTR 看似下降。
> 2. **多目标冲突的延续** —— 你之前怀疑时长目标跟 CTR 冲突。embedding 维度变大后，时长目标的表征空间也更丰富，可能加剧了冲突。
>
> 不如先在一个小流量上同时监控 CTR 和时长，看看是否负相关。排除这两个原因后，再考虑过拟合问题。"

---

## 三、差异点对比

| 维度     | 没有 mem0          | 有 mem0                    |
| ------ | ---------------- | ------------------------- |
| 问题诊断深度 | 泛泛而谈"可能过拟合"      | 结合历史排查的根因（热加载问题、多目标冲突）    |
| 历史实验记忆 | 不知道前因后果          | 记得你试过 content 特征无效，建议不走弯路 |
| 团队上下文  | 不知道你在做双塔、AB 平台特性 | 知道你的技术栈和平台坑，建议切合实际        |
| 决策效率   | 每次都要重复背景信息       | 一次沟通，长期记忆，逐步积累模型诊断经验      |
| 协作价值   | 每轮都是独立对话         | 知识逐步沉淀，新成员也能看到历史分析链路      |

**实际工作中意味着什么：**

- **没有 mem0 时**，LLM 助手每次都是"新人"，不记得你上周调过什么参数、踩过什么坑、得出了什么结论，每次都要重新交代上下文。
- **有了 mem0**，助手像跟了你两个月的同事——知道你的模型架构、实验平台坑点、之前试过的方案，建议能建立在之前的讨论基础上，而不是每次都从零开始。

## 四、核心问题：mem0 相对于 Agent 自身记忆的增量

### 4.1 关键结论：Claude Code 等 Agent 没有跨会话记忆

Claude Code 的文档明确说明它"**forgets everything between sessions**"——这正是 Mem0 插件要解决的问题：

> "Claude Code forgets everything between sessions. This plugin fixes that. Install it, work normally, and Claude remembers what happened across sessions."

所以：**没有 mem0 的话，Claude Code 里找不到那些项目记忆。一个 session 关了，所有上下文就丢了。**

### 4.2 mem0 相对于 Agent 自身记忆的增量

| 维度     | 没有 mem0（仅 Agent 自身记忆）            | 有 mem0                             |
| ------ | -------------------------------- | ---------------------------------- |
| 会话间持久性 | ❌ 关闭 session 全部丢失                | ✅ 跨 session 自动保留                   |
| 记忆粒度   | 原始对话文本（token 开销大）                | ✅ 提取后的结构化事实，去重、精炼                  |
| 检索方式   | 只能拼完整历史到 prompt（长度有限）            | ✅ 语义搜索 + 关键词 + 实体匹配 + 时间感知         |
| 记忆规模   | 受限于 context window（~200K tokens） | ✅ 向量存储，无上限                         |
| 多用户隔离  | 不适用（单用户环境）                       | ✅ user_id / agent_id / app_id 三层隔离 |
| 共享团队记忆 | ❌ 无法在多人间共享                       | ✅ 项目知识归一池，团队成员共享                   |
| 记忆管理   | 只能靠对话手动回顾                        | ✅ 可分类、搜索、删除、导出、反馈                  |

### 4.3 三个场景的具体说明

**场景一：没有 mem0**

- Session 1：你跟 Claude Code 讨论双塔模型、CTR 掉 0.3%、AB 实验平台问题，聊了 30 分钟得出结论，然后关掉终端下班。
- Session 2（第二天）：你重新打开 Claude Code 问"上周把 embedding 维度从 64 调到 128，线上 CTR 降了 0.1%，什么情况？"——Claude Code 完全不记得前一天的讨论。它不知道你负责召回、怀疑过热加载、试过 content 特征、AB 平台有 hash 分桶偏移。你只能重新说一遍背景，或接受一个泛泛的回答。

**场景二：有 mem0（Claude Code 插件）**

- Session 2（第二天）：你输入上面的问题。在回答前，插件自动用你的 prompt 搜索 mem0，检索出 5 条相关记忆注入上下文（双塔+FM、CTR 掉 0.3%、content 特征无效、多目标冲突、AB 平台 hash 分桶偏移 + 热加载 serving 不一致）。Claude Code 给出回答时，已经知道所有上下文。

**场景三：团队协作（Mem0 独有增量）**

- 这是 Agent 自身记忆**永远做不到**的事：你的同事在 Session 3 中问"我们推荐系统 AB 实验的 bucketing 方案是什么？"——因为 Mem0 把项目知识存在 agent_id（项目身份）下的共享池中，你的同事也能搜索到你之前关于 AB 实验的讨论记录。团队集体知识逐渐沉淀，而不是散落在每个人的本地 session 里。

---

## 五、一句话总结

> **Agent 自身记忆 = 当前会话的短期记忆（关了就忘）**  
> **Mem0 = 持久化的长期记忆 + 语义检索 + 团队共享 + 跨工具可用**

你看到的那些提取出来的记忆（双塔模型、CTR 分析、AB 实验坑点），没有 mem0 的话，在 Claude Code 的第二天 session 里是**完全不存在**的。这就是 mem0 带来的增量。

## 六、追问：记忆增量分析与提取指令优化

> 针对上面的推荐研发例子，进一步做了三件事：① 分析项目记忆增量；② 优化记忆提取指令；③ 汇总成本文档。本节覆盖前两项，第三项即本 MD 本身。

### 6.1 动作前的数据检查

- 项目数据**尚未触发自动分析**（自动分析需 50 条记忆，当前只有 29 条）。
- 但已有的 29 条记忆**足够手动分析和优化**，先读完当前数据。
- 动作步骤包括：分析新增事件以发现提取缺口、分析记忆以进行分类、读取项目配置。
- 读取后发现：当前 `custom_instructions` 为 **null**，即提取尚未做任何领域定制——这正是可优化的入口。

### 6.2 一、记忆增量分析

**基础事实对比**（以推荐研发工程师的两轮对话为例）：

| 项目知识                                 | 没有 mem0 时 Session 2 是否可知 | 有 mem0 后是否记住 |
| ------------------------------------ | ------------------------ | ------------ |
| 你负责召回策略，双塔模型 + FM                    | ❌                        | ✅            |
| CTR 掉过 0.3%，怀疑冷启动                    | ❌                        | ✅            |
| 试过 title embedding 做 content 特征，效果不好 | ❌                        | ✅            |
| 怀疑多目标优化中时长目标与 CTR 冲突                 | ❌                        | ✅            |
| AB 实验平台用 hash user_id 分桶，线上有偏移       | ❌                        | ✅            |
| 怀疑模型热加载导致线上 serving 不一致              | ❌                        | ✅            |
| 实验流量从 10% 提到 30%，观测周期从 2 周缩至 5 天     | ❌                        | ✅            |

> 注：上表在原始推荐研发例子的 6 条记忆基础上，补充了「实验流量 10%→30%、观测周期 2 周→5 天」这一条，共 7 条核心事实。

**结论：** 分析的 15 条记忆中，**14 条是纯增量**（助理建议的那 1 条实用价值较低，属于可优化的点）。

**当前提取质量分析：**

✅ **做得好的：**

- 技术事实提取准确（模型架构、指标变化、实验参数）
- 因果关系保留（"怀疑是因为……"、"导致……"）
- 关键数字保留（0.3%、10%→30%、2 周→5 天）

⚠️ **可优化的：**

- 存了 2 条 "Assistant recommended……" —— 这是助理自己的建议，不是用户事实，占空间且无检索价值
- `memory_depth` 为 "1"（Less），部分细节被截断
- 分类用默认标签（technology、misc），粒度太粗，没有领域感
- 缺少「实验结论」或「验证结果」这类对研发工作最有价值的记忆类型
- 同一实体（如 AB 实验问题）被拆成 2 条独立记忆，缺少关联

### 6.3 二、优化记忆提取指令

基于上面的分析，推荐两件事一起改——

**2.1 自定义分类体系**

| 分类                    | 说明                        |
| --------------------- | ------------------------- |
| `model_architecture`  | 模型结构、特征工程、embedding 维度等   |
| `experiment_results`  | CTR/AUC 变化、AB 实验结论、离线在线指标 |
| `hypothesis_analysis` | 根因假设、因果推断（怀疑……因为……）       |
| `infra_bottlenecks`   | 平台限制、serving 问题、部署相关      |
| `team_decisions`      | 团队技术选型、架构评审结论             |

**2.2 优化提取指令**

当前 `custom_instructions` 为 null，按模板格式设计一套（英文原指令已译为中文）：

> **请记住以下内容：**
>
> - 用户的模型架构细节，例如双塔、FM、embedding 维度、特征工程方法。
> - 实验结果，包括指标变化（CTR、AUC 等）、实验周期、流量分配，以及结果是否显著。
> - 用户形成的根因假设及其推理链（怀疑 X 是因为 Y）。
> - 基础设施约束，例如 AB 实验平台行为、serving 不一致、部署难题。
> - 之前尝试过的方案及其结果（试过 X 但收效甚微）。
> - 用户在推荐系统中的角色、团队背景、项目归属。
>
> **请不要记住以下内容：**
>
> - 助理自身提出、但未被用户确认或采纳的建议或推荐。
> - 没有任何技术含量的通用问候、闲聊、客套话。
> - 用户明确放弃、且未进一步排查的过时中间步骤或死胡同思路。

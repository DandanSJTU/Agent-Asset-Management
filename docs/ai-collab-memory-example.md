# AI 协作记忆增量演示：以「设计 AI 协作的前端页面和后端数据」为例

> 本文用「给 AI 协作提一个功能设计需求」的工作场景，说明 **AI 协作接入记忆层** 相对于 **无记忆直接提问** 带来的增量价值，并澄清一个常见误解：**纯 LLM 直接提问在会话之间是「失忆」的**——关掉会话，所有上下文就没了。

## 一、场景设定

假设你在「AI 协作」里已经跟 AI 协作过一段时间，沉淀了以下关于你的记忆：

- 你是携程 Trip **首页信息流推荐策略 PM**，负责 T 站 + C 站双平台
- 你偏好**深蓝金配色、单文件自包含 HTML、结论先行、y=f(x)、简单可解释可落地**
- 你在做 **TencentDB-Agent-Memory**（展示名 Agent 资产管理），资产库 = **Skill / 记忆 / Wiki** 三套
- 技术栈：**MemoryPanel（React + tea 组件库）+ MemoryCore（8420）+ knowledge 服务（8424）**，sqlite 后端
- **AI 协作**是要在面板新增的 tab，目标是比较「直接提问 vs 检索资产库」两种回答
- 你已产出「AI 协作对比 demo」原型，形式是**双栏对比「直接提问 vs 检索资产库」**

## 二、对话示例：设计 AI 协作的前端页面和后端数据

新的一轮问题：

> "帮我设计 AI 协作的前端页面和后端数据。"

### 2.1 没有记忆（失忆模式）

LLM 只看到你最新这条消息，对你一无所知：

> "可以做一个聊天式界面：左侧会话列表，中间对话区，右侧『记忆设置』面板可开关『启用长期记忆』；顶部输入框 + 发送按钮，消息用气泡区分用户 / AI。后端用 `POST /api/chat` 收问题、`GET/POST /api/memory` 存取记忆，用向量数据库（如 Milvus / Pinecone）存对话 embedding 做语义检索；表结构建 `users`、`conversations`、`messages`、`memories`；前端 React + Ant Design，后端 FastAPI / Node，数据库 PostgreSQL + 向量扩展。"

回答很通用——因为它不知道你在做 Agent 资产管理、不知道你的技术栈是 React+tea、不知道你偏好深蓝金、也不知道你已跑通双栏对比原型，只能给一份套在任何产品上都成立的 SaaS 设计稿。

### 2.2 有记忆

检索到相关记忆后，prompt 里会注入上述 6 条事实。LLM 拿到上下文后，回答完全不同：

> "等一下——这个需求不用从零设计。你做的 Agent 资产管理，资产库里已经有记忆 / 技能 / Wiki 三套检索能力，而且你已经跑通了『直接提问 vs 检索资产库』的双栏对比原型。我按你现有的 MemoryPanel 架构和深蓝金配色来设计，直接复用现有接口和数据模型，不引入新中间件。
>
> **前端**：在 `constants/menu.tsx` 加 `ai_collab` 项、`routes/index.tsx` 加 `{ path:'ai-collab', element:<AiCollabPage/> }`，复用 ConsoleLayout；布局是顶部问题输入 + 『检索资产库』开关，下方双栏——左『直接提问』、右『检索资产库后的回答』（就是你的 demo 结构），右侧带检索轨迹（wiki / skills / memories 命中 chip）+ 增强回答。组件复用 tea 的 `SearchBox` / `Table` / `Button`，深蓝金主题。
>
> **后端**：检索层直接复用 `personal-space/memories`(GET)、`knowledge/wiki/search`(POST)、`personal-space/skills`(GET)，不用新搭索引；新增 `/api/v1/ai-collab/ask` 做『检索 → 拼 prompt → 调你已配的 DeepSeek 生成』。持久化用现有 sqlite：加 `ai_collab_sessions`、`ai_collab_messages`（含 `retrieved_asset_ids` 字段，可回溯这次回答用了哪些记忆）、`ai_collab_feedback` 三张表。
>
> 这样完全贴合你『结论先行 / y=f(x) / 简单可解释可落地』的标准，落地成本也低——前端只是现有 panel 加一个 tab，后端只是复用现有检索接口。"

## 三、差异点对比

| 维度 | 没有记忆（失忆） | 有记忆 |
| --- | --- | --- |
| 需求理解深度 | 泛泛套通用 SaaS 方案 | 接住你是在做 Agent 资产管理、AI 协作是要新增的 tab |
| 历史上下文记忆 | 不知道你的技术栈和偏好 | 记得 React+tea、深蓝金、结论先行、y=f(x) |
| 项目资产贴合度 | 不引用任何你的真实资产 | 复用 personal-space / wiki / skills 接口、接住已产出原型 |
| 决策效率 | 每次都要重新交代背景 | 一次沟通，长期记忆，逐步累积项目设计经验 |
| 协作价值 | 每轮都是独立对话 | 知识逐步沉淀，同事也能搜到你之前的设计讨论 |

**实际工作中意味着什么：**

- **没有记忆时**，AI 助手每次都是"新人"，不记得你做什么产品、用什么技术栈、有什么设计偏好，每次都要重新交代上下文，拿到的是一份放之四海皆准的通用稿。
- **有了记忆**，助手像跟了你两个月的同事——知道你的产品定位、技术栈、审美偏好和已产出的原型，建议能建立在之前的讨论基础上，而不是每次都从零开始。

## 四、核心问题：记忆 相对于「无记忆直接提问」的增量

### 4.1 关键结论：无记忆直接提问在会话之间是「失忆」的

主流 LLM 对话（不接记忆层）的本质是：**关掉会话，所有上下文就丢了**——这正是「AI 协作 + 记忆」要解决的问题。

> "A plain LLM chat forgets everything between sessions. Memory fixes that. Connect it, and the AI remembers who you are and what you've built across sessions."

所以：**没有记忆的话，AI 协作在下一轮对话里完全不记得你是携程推荐 PM、在做 Agent 资产管理、偏好深蓝金。一个 tab 关了，这些上下文就没了。**

### 4.2 记忆 相对于 无记忆直接提问 的增量

| 维度 | 没有记忆（仅当前会话） | 有记忆 |
| --- | --- | --- |
| 会话间持久性 | ❌ 关闭会话全部丢失 | ✅ 跨会话自动保留 |
| 记忆粒度 | 每次重新交代背景（token 开销大） | ✅ 提取后的结构化事实（身份 / 偏好 / 项目） |
| 检索方式 | 只能靠你每次复述上下文 | ✅ 语义检索 + 关键词 + 实体匹配，自动注入 |
| 记忆规模 | 受限于单次对话 context window | ✅ 持久化存储，无上限 |
| 多用户隔离 | 不适用（单用户环境） | ✅ user_id 隔离（personal-space 按用户归池） |
| 共享团队记忆 | ❌ 无法在多人间共享 | ✅ 资产库归一池（skill / memory / wiki 团队共享） |
| 记忆管理 | 只能靠对话手动回顾 | ✅ 可分类、搜索、删除、导出、反馈 |

### 4.3 三个场景的具体说明

**场景一：没有记忆**
- Session 1：你跟 AI 讨论 Agent 资产管理的架构、技术栈（React+tea / MemoryCore / knowledge）、设计偏好（深蓝金 / 结论先行），聊了 30 分钟得出结论，然后关掉页面下班。
- Session 2（第二天）：你重新打开问"帮我设计 AI 协作的前端页面和后端数据"——AI 完全不记得前一天的讨论。它不知道你做 Agent 资产管理、不知道 tea 组件库、不知道深蓝金偏好、不知道你已产出双栏对比原型。你只能重新说一遍背景，或接受一个泛泛的 SaaS 稿。

**场景二：有记忆（接入记忆层）**
- Session 2（第二天）：你输入上面的问题。在回答前，记忆层自动用你的 prompt 检索，注入 6 条相关记忆（身份=携程推荐 PM、偏好=深蓝金/结论先行、项目=Agent 资产管理、技术栈=React+tea+MemoryCore、目标=AI 协作 tab、已产出对比原型）。AI 给出回答时，已经知道所有上下文，直接产出贴合你项目的可落地方案。

**场景三：团队协作（记忆层独有增量）**
- 这是无记忆直接提问**永远做不到**的事：你的同事在 Session 3 中问"AI 协作的检索接口怎么接？"——因为记忆层把项目知识存在共享池中，你的同事也能搜索到你之前关于 `personal-space/memories`、`knowledge/wiki/search`、`personal-space/skills` 的讨论记录。团队集体知识逐渐沉淀，而不是散落在每个人的本地会话里。

---

## 五、一句话总结

> **无记忆直接提问 = 当前会话的短期记忆（关了就忘）**
> **AI 协作 + 记忆 = 持久化的长期记忆 + 语义检索 + 项目 / 团队共享 + 跨会话可用**

你看到的那些注入的记忆（携程推荐 PM、深蓝金偏好、React+tea 技术栈、已产出对比原型），没有记忆的话，在下一轮会话里是**完全不存在**的。这就是记忆带来的增量。

## 六、追问：把「带记忆」从演示变成真实能力 + 记忆提取优化

> 针对上面的 AI 协作例子，进一步做了两件事：① 验证记忆层接口可用性；② 优化记忆提取指令。本节覆盖这两部分。

### 6.1 动作前的数据检查

- 记忆层接口**本机已验证可用**：`GET /api/v1/personal-space/memories`（Header `X-Tdai-Service-Id` + `X-Tdai-User-Key`）可拉取个人记忆；`POST /api/v1/knowledge/wiki/search`、`GET /api/v1/personal-space/skills` 可拉取 Wiki / 技能。
- 当前 **AI 协作 tab 尚未真实落地**，"有记忆"路径只是在 Demo 里人工整理记忆注入，待接入运行时实时检索。
- 动作步骤：验证接口 → 设计检索→注入→生成两段式 → 定义持久化表（含 `retrieved_asset_ids` 可追溯）→ 读项目记忆配置确认提取粒度。

### 6.2 一、记忆增量分析

**基础事实对比**（以 AI 协作设计需求为例）：

| 项目知识 | 无记忆时 Session 2 是否可知 | 有记忆后是否记住 |
| --- | --- | --- |
| 你是携程推荐 PM，负责 T 站 + C 站双平台 | ❌ | ✅ |
| 你偏好深蓝金、单文件 HTML、结论先行、y=f(x) | ❌ | ✅ |
| 你在做 Agent 资产管理，资产库 = Skill/记忆/Wiki | ❌ | ✅ |
| 技术栈 MemoryPanel(React+tea)+MemoryCore+knowledge | ❌ | ✅ |
| AI 协作是要新增的 tab，目标是对比两种回答 | ❌ | ✅ |
| 你已产出双栏对比 demo 原型 | ❌ | ✅ |
| 你要求「简单可解释可落地」的评估标准 | ❌ | ✅ |

> 注：上表在场景设定的 6 条记忆基础上，补充了「评估标准」这一条，共 7 条核心事实。

**结论：** 上面 7 条项目知识中，**7 条全部是纯增量**——无记忆时 AI 一条都不知道，有记忆后全部可用，且直接决定了回答是从零泛泛还是贴合项目。

**当前提取质量分析：**

✅ **做得好的：**
- 身份与角色提取准确（携程推荐 PM、双平台）
- 偏好与标准保留（深蓝金、结论先行、y=f(x)、可落地）
- 项目与技术栈关联保留（Agent 资产管理、React+tea、MemoryCore）
- 已产出产物记入记忆（对比 demo 原型），便于后续复用

⚠️ **可优化的：**
- 记忆粒度偏粗，缺少「资产 API 契约」这类对开发最有价值的记忆类型（如各接口的请求/响应字段）
- 同一项目（Agent 资产管理）的相关事实散在多条记忆里，缺少关联与统一项目标识
- 缺少「决策结论」类记忆（如"AI 协作采用双栏对比而非单栏"这一已拍板的方案）
- 部分记忆是用户自述，未标记置信度与来源，检索时难以排序

### 6.3 二、优化记忆提取指令

基于上面的分析，推荐为 AI 协作场景设计一套领域分类与提取指令——

**2.1 自定义分类体系**

| 分类 | 说明 |
| --- | --- |
| `identity_preference` | 用户身份、角色、审美与交付偏好（深蓝金、单文件 HTML、结论先行） |
| `project_context` | 项目定位、资产库构成、当前在做的模块（Agent 资产管理、AI 协作 tab） |
| `tech_stack` | 技术栈与部署形态（React+tea、MemoryCore、knowledge、sqlite 后端） |
| `asset_api` | 资产检索接口契约（personal-space/memories、wiki/search、skills 的请求响应） |
| `prototype_artifact` | 已产出的原型与产物（对比 demo、设计文档）及其结论 |
| `eval_standard` | 用户要求的评估标准（简单、可解释、可落地、y=f(x)） |

**2.2 优化提取指令**

当前记忆提取若未做领域定制，可按模板设计一套（译为中文）：

> **请记住以下内容：**
> - 用户的身份与角色，例如携程推荐策略 PM、负责双平台。
> - 用户的交付与审美偏好，例如深蓝金配色、单文件自包含 HTML、结论先行、y=f(x)。
> - 用户正在做的项目背景，例如 Agent 资产管理、资产库构成、当前模块目标。
> - 用户的技术栈与部署形态，例如前端框架、后端服务、存储后端。
> - 用户已拍板的方案结论（如"采用双栏对比"），而非仅记录讨论过程。
> - 用户明确定义的评估标准，例如简单 / 可解释 / 可落地。
>
> **请不要记住以下内容：**
> - 助理自身提出、但未被用户确认或采纳的建议或推荐。
> - 没有任何项目价值的通用问候、闲聊、客套话。
> - 用户明确放弃、且未进一步推进的过时中间步骤或死胡同思路。
